# 知识快照同步失败恢复

> **文档状态：** 当前有效
> **适用对象：** 系统管理员、开发者
> **维护基准：** 2026-09-22 内网版本

## 保存与同步边界

数据库保存成功与快照导出成功分别表达。板块、字段、知识库和知识条目的增删改，由数据库触发器在同一事务中递增同步 revision；业务事务回滚时 revision 一起回滚。导入发现来源字段、热点词条新增等直接数据库写入也会被记录，不依赖单一 HTTP 路由触发。

数据库版本 5 新增 `knowledge_sync_outbox`，存储当前 revision、已导出 revision、基线哈希、待写快照哈希及失败标记，不存储模型密钥或额外聊天内容。现有知识内容哈希仍按排序后的配置生成，不使用导出时间。revision 可以因派生字段变化而递增，但无实质变化的导出不会重复改写 catalog 文件。

导出过程：记录预期快照哈希 → 原子替换 catalog → 写状态文件 → 确认已导出 revision。数据库已提交但进程未导出就退出时，重启发现待同步 revision；catalog 已替换但状态文件未写完时，通过 pending 哈希识别本机写入，避免误判为仓库冲突。

仓库文件与本机基线/pending 哈希均不相同时，拒绝覆盖文件；保留数据库和仓库两份修改。启动遇到真正冲突仍停止，请先备份并按既有流程合并，重试接口不会自动解决冲突。

## 页面与接口

主工作台及知识工作台显示三类状态：快照已生成、等待同步、仓库冲突。页面每 5 秒串行查询，卸载后取消；重试按钮只生成快照，不重新提交知识导入、配置保存或模型分析。

| 接口 | 行为 |
| --- | --- |
| `GET /api/knowledge-sync` | 查询本地快照状态、最后导出时间与错误标记 |
| `POST /api/knowledge-sync/retry` | 重试导出；冲突返回 409，导出失败返回 503，本地数据保留 |
| 配置保存接口 | 数据库成功时保留 success/data，附加 sync 状态；快照失败不再把已保存数据报告为保存失败 |

热点分析已成功、仅快照失败时保持分析 completed，交由同步状态处理，避免用户为了生成快照再跑付费分析。技术性模型失败与业务需复核的进一步分类不在本次变更中。

“快照已生成”不等于 GitHub 已上传；接口 `github=not_checked`，页面明确未检查推送状态。手动 Git 提交/推送或 `npm run knowledge:push` 仍负责远端同步。本次代码发布不包含用户尚未提交的 catalog 内容。

## 恢复与限制

- 可恢复的快照写入失败在重启时尝试一次；权限/磁盘问题持续时保留 pending，服务可启动供用户查看和重试。没有高频后台自动重试写磁盘。
- 文件被删除、格式损坏或真实合并冲突应先恢复/合并文件，不以覆盖仓库文件解决。
- `knowledge/catalog.json` 是导出快照与恢复源，不是配置定义源：不要在 Git 中手工编辑已提交快照；结构调整通过新增迁移完成，再启动服务导出新快照。
- 状态和文件写入仍不是跨介质原子事务，依靠持久化意图和哈希恢复；磁盘本身损坏仍需要完整备份。
- 适用本地单实例与可信文件目录。Git 并发操作仍应遵守停止服务、检查工作区和快照冲突的操作要求。
- 版本 5 数据库不能直接交给版本 4 旧代码运行；回退先停止服务，保留新数据，使用迁移前保护数据库/完整备份恢复到另一目录，并匹配原独立密钥。
