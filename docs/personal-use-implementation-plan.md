# 个人使用阶段风险与实施方案

## 目标

在保持 SQLite、本地文件和单用户模式的前提下，让项目稳定完成：

```text
模型配置 → Excel 导入 → 截图解析 → 批量任务 → 人工复核 → Excel 导出
```

同时保证知识库可以通过 GitHub 快照在不同环境恢复。

## 当前风险清单

| 风险 | 影响 | 概率 | 当前应对 |
|---|---|---:|---|
| 5173 开发前端未代理 `/api` | 页面能打开但接口数据为空 | 高 | 配置 Vite proxy；个人使用优先访问 8787 生产构建 |
| 前端和后端需要分别启动 | 重启后容易只启动一端 | 高 | 增加统一 `start` 和一键启动脚本 |
| 模型配置为空或角色配置错误 | 导入后无法解析 | 高 | 增加配置检查、连接测试和首次使用提示 |
| API Key 泄露或密钥丢失 | 模型账号风险，已有配置无法解密 | 中 | API Key 只存本地；生产强制独立密钥；增加密钥备份说明 |
| SQLite 文件损坏或误删 | 任务、复核结果和本地数据丢失 | 中 | 自动备份、恢复命令和启动完整性检查 |
| 大 Excel 占用过多磁盘或内存 | 导入失败、服务卡顿 | 中 | 限制文件大小、监控磁盘、保留流式导入、定期清理 |
| 外部模型超时、限流或返回格式错误 | 记录失败或结果不完整 | 高 | 超时、重试、备用模型、失败记录重试和并发可调 |
| 知识库快照和本地数据库冲突 | 配置被覆盖或无法保存 | 中 | 现有冲突保护；操作前先 pull，冲突时手工合并 |
| 知识库 JSON 含业务分类数据 | GitHub 仓库泄露业务知识 | 中 | 仓库设为私有；禁止提交聊天截图和 API Key；审查提交内容 |
| 编码或文件名异常 | 中文板块、Excel 文件名显示错误 | 中 | 全链路 UTF-8；继续保留编码回归测试 |
| 服务异常退出 | 页面无法访问，后台任务中断 | 中 | 日志、自动重启脚本、启动健康检查 |
| 单用户设计被误用于多人生产 | 数据互相覆盖或权限缺失 | 低（当前） | README 明确单机范围；上线前再做权限和数据库升级 |

## 实施阶段

### 阶段 0：基线和备份

1. 复制 `data/app.db` 到 `data/backups/`。
2. 执行 `npm run knowledge:export`，确认 `knowledge/catalog.json` 已更新。
3. 确认 Git 工作区干净，并推送当前代码和快照。
4. 记录 Node.js、npm、项目提交号和当前数据库大小。

验收：能够从当前 Git 提交和数据库备份恢复到现状。

### 阶段 1：统一启动和开发访问

1. 在 `vite.config.ts` 增加 `/api` 到 8787 的 proxy。
2. 增加生产启动命令，构建后由 Express 托管 `dist`。
3. 增加 Windows 一键启动脚本，检查端口、依赖和日志目录。
4. 保留 `http://localhost:8787/` 作为个人使用的统一入口。

验收：只执行一次启动命令，页面、板块接口和健康检查均正常。

### 阶段 2：模型配置和真实链路

1. 配置视觉模型和文本模型。
2. 分别执行连接测试，确认用途默认值正确。
3. 使用脱敏 Excel 验证导入预览、图片提取和中文字段。
4. 先单条分析，再执行 5-20 条小批量分析。
5. 验证暂停、取消、失败重试、人工复核和导出。
6. 保存一份真实验收文件的字段结果和错误日志。

验收：至少完成一轮真实模型端到端流程，导出的 Excel 可打开，图片和字段结果完整。

### 阶段 3：数据保护和可靠性

1. 增加 `npm run backup`，备份 SQLite、知识快照和配置说明。
2. 增加 `npm run restore`，恢复前自动生成旧数据库备份。
3. 增加数据库完整性检查和知识库索引重建命令。
4. 设置日志轮换和导入文件清理策略。
5. 保留最近 7 份数据库备份，按周清理更旧备份。

验收：删除测试数据库后，能够从备份恢复任务、知识库和检索索引。

### 阶段 4：日常 GitHub 同步

日常修改知识库后执行：

```powershell
cd "E:\客服解析中心\customer-chat-analysis-center"
npm run knowledge:push
```

换环境更新：

```powershell
git pull --ff-only
npm install
npm run build
npm run dev
```

如果提示同步冲突：

1. 停止服务。
2. 合并 `knowledge/catalog.json`，保留稳定 ID 和关联关系。
3. 运行 `npm run knowledge:restore`。
4. 检查板块、字段、知识条目和检索结果。
5. 再启动服务。

禁止直接强制推送，禁止把 `data/`、`.env`、聊天 Excel 和截图加入提交。

## 个人使用阶段的运行规则

- 单用户、单实例运行。
- 同一时间只执行一个大型导入或批量解析任务。
- 大文件导入前确认 `data` 所在磁盘空间充足。
- 模型限流或超时时先降低并发，再重试失败记录。
- 修改知识库前先执行 `git pull --ff-only`。
- 每次重要知识库修改后立即执行 `npm run knowledge:push`。
- 每周检查一次数据库备份和 GitHub 快照是否可以读取。

## 暂不实施的内容

个人阶段暂不引入：

- 多用户登录和权限系统
- PostgreSQL
- 对象存储
- 分布式任务队列
- 多实例部署
- 在线实时协同编辑

这些内容在团队上线前，根据并发量、数据量和权限要求重新设计。

## 团队上线前的触发条件

满足以下任一条件时，开始生产架构升级评估：

- 两个以上用户需要同时操作同一知识库。
- 单机 SQLite 出现锁等待或写入瓶颈。
- 任务量需要持续后台运行并跨进程调度。
- 聊天截图和结果需要集中存储或跨机器访问。
- 需要用户权限、审计记录或数据隔离。
- 需要 HTTPS、统一登录、限流和正式监控。
