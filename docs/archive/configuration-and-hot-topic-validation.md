# 配置 Schema 与热点错误分类

## 配置写入

服务层共享 `security/configuration-input.ts` 的 Zod Schema，在写库前校验类型、枚举、大小和关联。配置对象中的未定义属性会被忽略，不直接写库；已知属性类型错误会返回明确错误，不把字符串或数字强制转成布尔值。

- 字段：限定 string/number/boolean/object、ai/knowledge_match/knowledge_extract；校验启用、图片和导出开关；候选数量 5–30；拒绝保留属性名称及控制字符。中文字段 Key 继续支持，沿用原长度/字符约束。
- 字段修改不能更换所属板块；保存时完成依赖拓扑检查，循环依赖不能先保存后才在分析时发现。
- 板块：输出 Schema 校验每个字段的类型、选项、required，并拒绝重复 Key；父板块必须存在，父子关系不能形成循环。修复原 SQL 永远写 is_enabled=1 的问题；保存停用状态有效，未传开关时保留原启用状态。
- 知识列：角色按枚举校验，拒绝空/重复角色、重复列名、缺失父列及父列循环。导入映射和规范化后的完整列配置均校验；直接服务调用也受约束。
- 知识条目：最多 200 列，每格必须是字符串、最多 32767 字符；不把对象/数字隐式转换为检索内容。数据库写入和 FTS 更新仍在原事务内。
- 模型：Base URL 只允许 HTTP(S)，拒绝嵌入账号密码、查询参数和片段；API Key 最大 4096 字符。支持本机 HTTP 模型地址，没有新增远端域名白名单。

此阶段限定配置与知识条目写入，不宣称每个业务 HTTP 接口都已完成统一 Schema。仓库 catalog 恢复继续使用独立快照校验器，历史导入/恢复的兼容格式没有强制批量重写。

## 热点分析状态

原逻辑将全部错误记为 needs_review，字段调度层又将非 completed 统一转换为 needs_review。本次同时修正两层，确保 field run、记录及任务汇总能识别技术失败。

| 情况 | 状态 |
| --- | --- |
| 网络、鉴权、证书、限流、请求预算、数据库写入失败 | failed |
| JSON/字段协议错误、问题数量越界、返回候选外 ID | failed |
| 模型明确返回 review、证据不足/包含个体标识、已有词条停用或分析期间配置变化 | needs_review |
| 分析和知识已落库，仅快照导出失败 | 保持 completed，独立显示同步 pending |
| 用户取消 | 继续沿用取消信号与运行 token 保护，不新增失败/复核结果 |

区分通过显式业务复核异常实现，不靠错误文本猜测网络失败。失败或需复核都不会新增知识条目或对话关联；事务失败仍回滚，原结果历史保留。没有因修复而重新运行历史模型调用或改写已有失败记录。
