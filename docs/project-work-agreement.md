# 项目工作约定

**日期：** 2026-09-25
**状态：** 生效
**适用范围：** 客服解析中心当前版本及后续功能开发
**关联文档：** [项目目录结构与后续开发规范](project-structure-and-development-guidelines.md)

## 1. 目的

本约定定义项目如何接收需求、建立工单、选择工作流程、实施改动和完成验收。

它不替代产品规格、架构决策、测试代码或发布指南。它只规定这些材料如何协作，以及项目事项如何持续进入、推进和关闭。

## 2. 权威来源

同一事项出现多个记录时，按以下职责判断：

| 内容 | 权威来源 |
| --- | --- |
| 当前工单编号、负责人、状态、优先级、依赖 | GitHub Issue |
| 用户行为、业务约束、验收条件 | 规格文档和 Issue 验收清单 |
| 架构选择和不可逆决策 | `docs/adr/` |
| 代码实现和代码审查 | Pull Request 及其提交 |
| 自动化验证结果 | 测试、构建、质量闸门输出 |
| 一次性人工验收和发布证据 | `docs/archive/` 或被忽略的本地证据目录 |

GitHub Issue 是项目进度和工单状态的唯一入口。仓库文档保存详细背景和长期约束，不再复制一套独立的工单状态。

## 3. 工作事项入口

项目事项不只来自预先规划的功能，也包括运行中发现的问题。

以下内容都可以进入 GitHub Issues：

- 用户提出的新功能或行为变更。
- 可稳定复现的 Bug。
- 代码 Review 发现的行为缺陷或高风险问题。
- 自动化测试、构建、迁移或发布门禁失败。
- 安全、数据完整性、性能和可恢复性风险。
- 需要明确范围和负责人才能推进的技术债。

### 3.1 默认处理行为

Agent 收到请求后，先判断它属于哪类事项：

| 请求类型 | 默认行为 |
| --- | --- |
| 询问进度、解释原因、讨论方案 | 不创建 Issue |
| 一两个文件内的小改动，约 50 行以内，不涉及接口、迁移或完整验证 | 可直接处理；必要时在现有 Issue 留备注 |
| 新功能、复杂修复、跨模块改动 | 查找或创建 Issue，再开始实施 |
| 测试失败、Review 问题、发布阻塞 | 更新已有 Issue，或创建对应的阻塞 Issue |
| 一次性实验、验证可行性、不会保留的原型 | 不创建正式工单，明确标记为临时工作 |

如果 GitHub 连接和权限可用，Agent 应先查找已有 Issue；没有匹配项时创建新 Issue。没有创建权限时，只生成 Issue 草稿并明确说明“尚未写入 GitHub”，不得把草稿说成已创建。

用户可以显式覆盖默认行为：

```text
这只是临时实验，不建工单。
先不要改代码，只讨论方案。
直接修这个小问题，不需要建票。
```

## 4. 标准工作流程

### 第一步：分诊

判断事项是否已有 Issue、是否需要规格、是否涉及权限、数据库迁移、备份、部署或人工验收。

如果已有 Issue，优先更新并沿用它，不重复创建同一事项。

### 第二步：澄清需求

需求不清、术语不一致、范围跨越多个模块或验收标准不明确时，自动使用 `grill-with-docs` 进行需求澄清。

澄清结果至少应明确：

- 要改变的用户行为。
- 不应改变的既有行为。
- 失败和边界情况。
- 数据、权限、审计和部署影响。
- 可执行的验收条件。

### 第三步：形成规格和决策

- 单模块、小范围变更可以直接写入 Issue。
- 跨模块或有长期影响的功能，应先形成规格。
- 领域术语不稳定时，使用 `domain-modeling`，必要时更新上下文文档。
- 重要架构选择写入 `docs/adr/`。
- 多步骤实施计划使用 `docs/superpowers/plans/`，并列出明确文件、命令和验收步骤。

### 第四步：创建或更新 Issue

Issue 标题应能说明结果，建议使用以下前缀：

```text
[Feature] 增加接待规则版本管理
[Bug] 修复截图行开始时间误判
[Release] 完成真实 XLSX 发布门禁
[Chore] 拆分共享领域类型
```

Issue 至少包含：

```markdown
## 目标

## 背景和范围

## 不在范围内

## Blocked by

## 验收条件

- [ ] ...

## 验证命令

## 关联文档、分支和 PR
```

### 第五步：拆分和实施

一个 Issue 应对应一个可独立验证的结果。需要多个实现步骤时，使用父 Issue 和子 Issue，或在 Issue 内使用 checklist。

拆分原则：

- 一个子任务应能单独说明完成条件。
- 明确 `Blocked by`，不要只依赖提交顺序。
- 不按前端、后端、测试机械拆分，优先按用户可验证行为拆分。
- 小任务留在父 Issue checklist 中，不为每个内部动作创建 Issue。

实现前按任务选择技能：

| 情况 | 默认技能 |
| --- | --- |
| 需求澄清和规格整理 | `grill-with-docs` |
| 领域术语、模块边界和架构设计 | `domain-modeling`、`codebase-design` |
| 多步骤实施计划 | `writing-plans` |
| 新功能或行为修复 | `test-driven-development` |
| Bug、测试失败、性能回退 | `diagnosing-bugs` 或 `systematic-debugging` |
| 完成实现后的审查 | `code-review` |
| 即将宣称完成或合并前 | `verification-before-completion` |

这些技能由 Agent 环境提供。项目只记录触发条件，不复制技能实现。技能不可用时，Agent 必须说明并执行等价的人工流程，不得假装已经调用。

### 第六步：验证和审查

实现完成后，先按风险运行最小相关测试，再运行项目要求的完整验证。涉及共享契约、数据库、导入导出或发布流程时，应扩大验证范围。

代码 Review 重点检查：

- 是否符合 Issue 和规格。
- 是否引入范围外的业务规则变化。
- 是否覆盖失败、重试、取消、重复点击和重启场景。
- 是否影响权限、审计、数据隔离和敏感信息。
- 是否更新迁移、文档、测试和发布证据。

### 第七步：关闭工单

只有满足以下条件，Issue 才能标记为 `done`：

- 代码和测试已合并或明确交付。
- 验收条件全部有结果。
- 相关自动化验证通过，失败项已明确归因。
- 必要的文档、迁移、配置和证据已更新。
- 必要的人工验收已完成。
- 没有未说明的阻塞项或未提交敏感文件。

## 5. 编号、状态和优先级

### 5.1 编号

GitHub Issue 的原生编号是全局工单编号。项目不在每个功能目录中重新从 `01`、`02` 开始编号。

本地文档引用 Issue 时使用：

```text
GitHub Issue #123
```

如果需要在离线材料中引用，可以写成 `Issue #123`，但不要创建第二套会与 GitHub 编号冲突的编号。

### 5.2 状态

| 状态 | 含义 |
| --- | --- |
| `triage` | 已进入队列，正在判断范围和优先级 |
| `ready` | 目标、依赖和验收条件明确，可以开始 |
| `in-progress` | 正在修改代码、测试或环境 |
| `in-review` | 实现基本完成，等待审查或补充验证 |
| `blocked` | 被外部条件、前置 Issue 或环境问题阻塞 |
| `done` | 所有验收条件和证据已完成 |

状态必须反映真实进度。不能因为代码已经提交，就把仍缺测试或人工验收的工单标记为 `done`。

### 5.3 优先级

| 优先级 | 含义 |
| --- | --- |
| `P0` | 当前发布、数据安全或核心运行被阻断 |
| `P1` | 高风险缺陷、重要业务行为错误或即将影响发布 |
| `P2` | 正常功能、一般缺陷和计划内改进 |
| `P3` | 低风险优化、体验改进和非紧急技术债 |

## 6. 本地文档和目录边界

新的大型事项可以在仓库中保存详细规格：

```text
docs/work-items/<initiative-name>/
├── spec.md
└── acceptance.md
```

这些文件应链接到对应 GitHub Issue，但不单独维护状态。

现有 `.scratch/` 中的局域网升级、发布收尾和历史过程材料暂时保留，不在迁移完成前大规模移动。后续新事项不再在功能目录下创建局部编号工单。

长期有效的操作说明放在 `docs/guides/`，重要架构选择放在 `docs/adr/`，一次性验收和发布材料放在 `docs/archive/`。本地 Excel、数据库、日志、真实业务样本和人工验收输出必须遵守 `.gitignore` 和项目安全约定。

## 7. 当前项目的验证要求

提交或合并前，根据改动范围运行必要命令：

```powershell
npm test
npm run typecheck
npm run lint
npm run build
npm run db:check
npm run smoke
npm run check:installation
```

涉及接待 XLSX 发布时，还必须运行：

```powershell
npm run gate:reception-xlsx
```

涉及局域网、容器、备份恢复或真实运行环境时，继续执行对应的 `scripts/` 验证脚本。

本地环境缺少数据库、真实样本或人工 Excel/WPS 验收条件时，应把它记录为环境阻塞或未完成证据，不能把自动化测试通过表述为正式发布完成。

## 8. 例外和变更

- 用户明确要求只讨论、不改代码时，停止在方案或规格阶段。
- 用户明确要求临时实验时，不创建正式 Issue，但要标记实验输出和有效期限。
- 紧急生产修复可以先修复再补 Issue，但必须在同一工作周期内补齐原因、影响、验证和回退记录。
- 工作协议本身发生变化时，更新本文档并在 GitHub 建立关联的维护 Issue。

本约定优先解决“事项没有入口、状态分散、工单重复编号和验收不闭环”问题；不要求为每一个小改动制造流程负担。
