# 局域网版本发布收口规格

**日期：** 2026-09-18

**范围：** 正式模型池基线、真实业务验收记录、提交与 CI 发布追溯

**明确不在本次范围：** HTTPS、内部 DNS、防火墙和互联网部署。这些内容仍属于后续基础设施工单。

## Problem Statement

客服解析中心已经可以在局域网中被多台电脑共同使用，并且已经用真实数据完成过导入、分析和导出。但当前项目仍存在三个发布收口问题：

1. 运行库中同时存在测试模型、测试供应商和正式供应商模型，普通管理员无法从系统状态中快速判断哪些模型属于正式路由基线。
2. 真实业务测试结果主要停留在实际操作事实，尚未形成完整、可追溯、脱敏的工单和验收记录。
3. 本地分支比远端分支多出最新提交，当前运行镜像与远端 CI 验证过的提交不是同一条来源链。

这些问题不会阻止当前局域网试用，但会降低正式交付、故障追溯和后续升级的可信度。

## Solution

按依赖顺序完成三个竖切交付：

1. 收敛正式模型池：确认正式供应商、默认文本模型和默认视觉模型，停用或移出测试模型，并保留可回退的配置与审计记录。
2. 补齐真实验收记录：将已完成的跨电脑真实数据导入、解析、导出结果写入验收记录；未实际执行的复核、备份恢复或基础设施检查必须继续标记为待完成。
3. 同步代码和文档提交到远端，重新执行 CI 质量闸门和发布工件构建，确认运行版本、提交 SHA、镜像标签和工件清单一致。

完成后，局域网版本可以被标记为“功能验收通过、等待 HTTPS/基础设施发布”的内部版本。

## User Stories

1. 作为管理员，我希望看到清晰的正式模型基线，以便知道当前解析实际会使用哪些文本和视觉模型。
2. 作为管理员，我希望测试供应商和桩模型不能参与正式路由，以免真实任务误调用测试服务。
3. 作为管理员，我希望默认文本模型和默认视觉模型都经过能力检测，以便系统就绪状态反映真实可用性。
4. 作为管理员，我希望模型池变更保留审计记录，以便追溯谁在什么时候启用、停用、验证或移除了模型。
5. 作为操作人员，我希望在正式模型池调整后仍能从其他局域网电脑导入真实 Excel 并完成解析。
6. 作为审核人员，我希望真实验收记录能说明复核、导出和数据状态分别是否已验证，而不是把部分验证误报成全流程通过。
7. 作为管理员，我希望真实验收附件不包含 API Key、密码、Cookie、加密密钥或完整业务数据。
8. 作为维护人员，我希望验收记录能关联到具体镜像、提交和运行时间，以便以后重现问题。
9. 作为开发人员，我希望远端 CI 验证当前局域网版本，而不是只验证旧提交。
10. 作为发布负责人，我希望发布工件中的提交 SHA、镜像标签、镜像 ID 和版本号一致。
11. 作为维护人员，我希望 CI 失败时不会生成可被误用的发布候选。
12. 作为项目负责人，我希望项目文档中的工单状态与实际运行事实一致，避免出现代码已完成但文档仍显示待提交的情况。

## Implementation Decisions

- 正式模型基线由管理员在运行主机上维护；工作站不得持有或提交模型 API Key。
- 模型基线至少包含一个已验证且可路由的文本模型和一个已验证且可路由的视觉模型。备用模型是否启用由管理员根据供应商配额和实际稳定性决定。
- 测试供应商、桩模型和临时验收模型不得出现在正式默认路由中；如需保留用于回归演练，必须停用或隔离，并在名称和文档中明确其非生产属性。
- 模型池清理必须优先使用现有的停用、移出路由池或删除接口，不直接修改 SQLite 文件；删除前必须确认没有违反历史引用和审计保留约束。
- 模型池变更前创建一份经过验证的主机备份，变更后检查 `/api/ready`、默认模型、池成员和最小真实解析。
- 真实验收记录采用“已通过 / 未执行 / 不适用 / 失败”四态，不允许用机器等价演练替代真实第二台工作站或真实供应商证据。
- 真实业务验收至少记录：入口、工作站、时间、样本脱敏说明、任务数量、解析记录数量、成功/失败数量、导出结果、模型供应商声明、审计事件和恢复证据状态。
- 真实验收附件只保存脱敏摘要、哈希、数量、状态和必要截图；原始业务文件、密码、API Key、Cookie、加密密钥不进入 Git。
- 提交同步以当前 `main` 为准。推送前先确认工作区干净、没有未审查的本地改动；推送后以 GitHub Actions 结果为质量事实来源。
- 发布候选必须满足：测试、类型检查、lint、构建、数据库初始化/检查和冒烟全部通过；工件清单中的提交 SHA、版本、镜像标签和镜像 ID必须与 CI 运行一致。
- 本次不改变 SQLite 单实例架构，也不引入 HTTPS、内部 DNS、防火墙或 PostgreSQL。

## Testing Decisions

- 模型池测试以用户可见路由状态和服务端事实为准：默认模型、验证状态、池启用状态、就绪状态和审计事件必须一致。
- 真实业务验收以跨工作站的外部行为为准，不以本机 API 脚本单独通过作为真实跨机证据。
- 文档验收检查工单 07、11、12 的状态、证据链接和待办是否与实际执行结果一致。
- CI 验收检查远端运行的提交 SHA 与本地待发布提交一致，并检查发布工件的 `manifest.json`。
- 继续执行现有质量闸门：`npm test`、`npm run typecheck`、`npm run lint`、`npm run build`、`npm run db:check`、`npm run smoke` 和安装检查。
- 所有测试和验收都必须避免真实凭据泄漏；模型供应商连接测试使用主机侧已保存凭据，工作站只引用供应商。

## Out of Scope

- 正式 HTTPS、内网 CA、DNS、防火墙和公网暴露边界。
- SQLite 到 PostgreSQL 的迁移。
- 多主机任务调度、分布式解析和 GPU 节点。
- 新增模型供应商适配器。
- 板块解析速度和 AI 字段合理性指标功能；该需求此前已被取消。
- 重写权限、审计、备份或模型池底层架构。

## Further Notes

- 当前实际验证已经证明局域网版本可以完成真实数据导入、分析和导出；本规格要求把事实转成可复查证据，不重复制造一套业务流程。
- 真实复核、备份恢复和基础设施检查若没有明确证据，必须保持未完成状态。
- 三张工单按 01 → 02 → 03 顺序推进；每张工单完成后都应保持工作区可验证。
