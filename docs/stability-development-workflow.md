# 项目稳定性开发流程

## 目标

将项目从“个人可运行工具”逐步提升为“个人稳定使用、可控失败、可恢复”的系统。
当前阶段只针对单用户、单实例、SQLite、本地文件和 OpenAI 兼容模型，不提前引入多人生产架构。

## 开发总原则

1. 先修复真实运行问题，再增加新功能。
2. 所有异步任务必须有开始、进行中、成功、失败、取消和恢复路径。
3. 所有模型供应商差异必须在连接测试阶段暴露，不能等批量任务才发现。
4. 所有数据库变更必须可重复执行、可追踪、可回滚。
5. 每项改动必须同时更新测试、文档和验收记录。
6. 默认保护本地数据，任何自动恢复或迁移都必须先备份。
7. 个人阶段不把聊天图片、任务记录、API Key 和分析结果提交到 Git。

## P0：批量任务可靠性

### 目标

解决批量任务卡在 `processing`、取消后状态不一致、失败记录无法重试和服务重启后任务丢失的问题。

### 实施顺序

1. 为每个任务增加明确的生命周期状态：`ready`、`processing`、`paused`、`cancelled`、`failed`、`completed`。
2. 为每次任务运行保存 `run_token`、开始时间、最后心跳和结束时间。
3. 每个模型请求必须有独立超时、AbortController 和最终清理逻辑。
4. 将临时错误分为：网络错误、超时、429、5xx；这些错误自动重试 2 次，间隔 5 秒、15 秒。
5. 将鉴权错误、参数错误、JSON 结构错误标记为不可自动重试。
6. 取消任务时停止新记录，等待或中断进行中的请求，并保证 `run_token` 最终释放。
7. 服务启动时扫描超过超时时间仍为 `processing` 的任务，恢复为 `failed` 或 `paused`。
8. 失败记录重试必须允许来源状态为 `failed`、`paused`、`cancelled`。
9. 任务最终状态必须由记录和字段运行结果重新计算，不能只依赖内存计数器。

### 验收标准

- 任务不会无限停留在 `processing`。
- 取消后可重试失败记录。
- 服务中途重启后，任务可以恢复或明确失败。
- 19 条测试数据在并发 1、批次 5 下可以完成，技术失败为 0。
- 连续点击启动不会产生两个相同任务运行。

## P0：模型能力检测和兼容层

### 目标

在模型配置阶段识别供应商不兼容问题，减少批量任务中的隐性失败。

### 实施顺序

1. 将“测试模型连接”拆成四个检查：普通文本、JSON 输出、视觉输入、错误响应解析。
2. 对每个用途保存检测结果和检测时间。
3. 视觉模型必须验证请求中确实包含 `image_url`。
4. 文本模型必须验证 JSON 输出能被解析为对象。
5. 检测 401、403、429、5xx、超时和 HTML 返回，显示明确原因。
6. 对不支持 `response_format` 的供应商自动切换到提示词约束，但必须再次验证 JSON。
7. 在模型配置页面显示“可用、部分兼容、不可用”状态。
8. 只有视觉和文本默认模型检查通过后，才允许启动批量分析。

### 验收标准

- 错误模型地址在保存后可以被识别。
- JSON 模式不再因供应商限制在批量过程中才失败。
- 视觉模型、文本模型分别通过对应能力测试。
- 备用模型可以完成同一能力检查。

## P1：数据库迁移和数据保护

### 目标

避免启动时隐式改库，确保升级和恢复可追踪。

### 实施顺序

1. 增加 `schema_migrations` 表。
2. 将当前启动迁移拆为编号迁移文件。
3. 每次迁移保存版本、执行时间和结果。
4. 迁移前自动执行数据库备份。
5. 迁移失败时停止启动，不继续写入业务数据。
6. 将板块种子数据、字段修复和业务数据迁移分开。
7. 把 `knowledge/catalog.json` 恢复放在数据库迁移成功之后。
8. 恢复前创建数据库备份，恢复使用事务。
9. 启动后执行完整性检查和外键检查。

### 验收标准

- 新数据库、旧数据库和已有知识库数据库都能完成升级。
- 同一迁移重复执行不会重复写入。
- 迁移失败后数据库仍可启动或能从备份恢复。
- `npm run db:check` 返回完整性正常、外键错误为 0。

## P1：知识库同步稳定性

### 规则

- Git 只同步板块、字段、知识库列映射和知识条目。
- 不同步模型配置、API Key、聊天截图、任务、分析结果和本地文件路径。
- 修改前先 `git pull --ff-only`。
- 冲突时停止编辑，手工合并后执行恢复。
- 不使用 `git push --force`。

### 开发要求

1. 快照增加 `version` 和生成时间。
2. 记录快照哈希和本地基线。
3. 启动恢复前显示恢复摘要。
4. 自动迁移产生的字段变化必须单独记录来源。
5. 快照格式变化必须增加版本迁移函数。
6. 为中文内容、重复路径、缺失板块和关联 ID 增加校验。

## P1：前端状态和错误处理

### 目标

降低 `App.tsx` 中异步竞态和状态互相覆盖的风险。

### 实施顺序

1. 抽离 `useJobs`：任务列表、任务切换和删除。
2. 抽离 `useRecordPager`：分页、筛选和记录详情。
3. 抽离 `useAnalysisPolling`：轮询、暂停、取消和恢复。
4. 抽离 `useImportJob`：上传、预览和导入进度。
5. 抽离 `useSectionConfig`：板块、字段和模型配置。
6. 统一请求错误对象，区分网络、鉴权、业务和冲突错误。
7. 对任务切换、重复点击和组件卸载增加取消请求处理。

### 验收标准

- 切换任务不会显示上一个任务的记录或详情。
- 刷新和切换板块不会覆盖未保存的人工复核编辑。
- 任务完成、失败、取消和暂停状态在刷新页面后保持一致。

## P1：上传、文件和日志安全

1. 校验 XLSX ZIP 结构和必要工作表关系。
2. 限制压缩包展开数量、单图大小、总图片大小和磁盘占用。
3. 所有上传文件使用随机内部路径，原始名称只作为显示信息。
4. 临时文件按任务清理，失败时也必须清理。
5. 增加磁盘空间检查，空间不足时拒绝导入。
6. 日志中禁止输出 API Key、完整请求正文和聊天内容。
7. 增加日志轮换和任务级错误 ID。
8. 默认只监听 localhost；绑定局域网前必须增加访问控制。

本地维护命令 `npm run maintenance` 默认清理超过 14 天的上传临时文件、知识库预览文件和日志，并在清理后执行数据库完整性检查。

## 测试策略

每项后端改动至少运行：

```powershell
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
npm.cmd run db:check
```

批量任务改动必须额外覆盖：

- 模型请求延迟
- 429 和 5xx
- 超时和 AbortController
- 取消中的任务
- 服务重启恢复
- 重复启动保护
- 失败记录重试

真实验收必须使用 20–50 条脱敏退款 Excel，记录模型服务、并发、批次、耗时、失败原因和导出文件。

## 发布流程

1. 创建功能分支。
2. 先写失败测试，再修改生产代码。
3. 本地完成类型检查、测试、构建和数据库检查。
4. 执行 `npm run backup`。
5. 执行 `npm run knowledge:export`，检查快照 diff。
6. 检查提交中没有 `.env`、API Key、`data/`、聊天截图和 Excel。
7. 提交并推送 GitHub。
8. 拉取到临时目录做一次新环境启动检查。
9. 再在个人环境重启服务。

## 当前执行顺序

1. 批量任务超时、取消和恢复。
2. 模型能力检测和 JSON 兼容性。
3. 真实 20–50 条退款 Excel 验收。
4. 显式数据库迁移版本。
5. 自动备份、恢复和日志轮换。
6. 前端状态拆分。
7. 上传安全强化。

## 不在当前阶段实施

- 多用户权限
- PostgreSQL
- 对象存储
- 分布式队列
- 多实例部署
- 在线协同编辑

这些内容等个人阶段稳定后，根据团队规模和并发数据重新设计。
